This page describes how we approach **reliability** at a conceptual level — for technical evaluators and partners who care about correctness under retries, duplicates, and partial failures. We don't document internal retry counts or timeouts; we focus on principles and behavior.

## Payment and idempotency

**Problem** — Networks and devices can retry. A customer might tap "Pay" twice, or the app might retry after a timeout. Without care, that could create duplicate charges.

**Approach** — Payment requests are **idempotent**. The backend sends a stable idempotency key (derived from order and payment context) to Square when creating the payment. Square treats duplicate requests with the same key as one payment. So:

- A single logical payment corresponds to at most one charge.
- Retries and duplicate taps don't result in double charges.

The same principle applies to loyalty and gift card actions at checkout — idempotency prevents rewards from being applied more than once per order.

## Order state and payment

Before creating a payment, the backend:

1. **Verifies** the customer's identity (valid phone-authenticated session token).
2. **Loads** the order and checks that it's in a payable state (pending payment).
3. If the order is already paid (or otherwise not payable), the backend returns a conflict response instead of calling Square again.

So even without idempotency, we avoid creating a second payment for the same order. Idempotency adds a second layer of protection for retries and duplicates.

## Square OAuth token refresh

Square OAuth tokens have a limited lifespan. The backend **automatically refreshes tokens before they expire**, so your Square connection stays active indefinitely. Merchants never need to reconnect Square or take manual action when tokens rotate. A notification is sent to Layout's accounts team whenever a Square reconnect occurs, for visibility.

## Catalog and location sync

- **Source of truth** — Square. We sync into the platform so the app and dashboard have current data.
- **Triggers** — Square webhooks (catalog version updated, location created/updated/deleted) drive near-real-time updates.
- **Daily scheduled sync** — A scheduled job runs every 24 hours as a backstop. Even if a webhook was missed or delayed, catalog and locations converge overnight. This ensures data accuracy without relying solely on event delivery.
- **Inventory** — `inventory.count.updated` webhooks patch sold-out flags on item variations in near real-time, so the app reflects what's actually available.
- **Scope** — All sync is per-tenant (per company). One merchant's data never overwrites another's.

## Loyalty and engagement reliability

- Loyalty balance and program data sync both on a schedule and after relevant checkout actions, ensuring the app displays accurate point balances.
- When a `loyalty.event.created` webhook fires (points earned), the backend queues a push notification job. Queuing decouples delivery from the webhook handler so a notification delay doesn't affect the checkout flow.

## Webhook verification

Incoming webhooks from Square are **verified** before processing using Square's HMAC signature. Invalid or tampered requests are rejected before any data is read or written. Each webhook is also routed to the correct tenant via a `merchantToCompany` lookup, ensuring events from one merchant never affect another's data.

## What we don't guarantee here

We don't document SLAs, uptime numbers, or RTO/RPO in this doc. The intent is to show that we **design for** idempotency, clear order state, auto-refreshing tokens, and verified webhooks so that payments and data stay correct under retries and failures. For formal SLAs or incident process, refer to your agreement or Layout's status page.

## Summary

| Area | Principle |
|------|------------|
| **Payments** | Idempotency keys with Square; order state checked before payment; no double charge on retries. |
| **Orders** | Single payable state per order; conflict response if already paid. |
| **Square tokens** | Automatically refreshed before expiry; no manual reconnect required. |
| **Catalog & locations** | Webhooks for near-real-time updates; daily scheduled sync as backstop; tenant-scoped. |
| **Inventory** | Near-real-time sold-out sync via `inventory.count.updated` webhook. |
| **Loyalty & push** | Loyalty sync on schedule and post-checkout; push notifications queued to decouple from webhook handling. |
| **Webhooks** | HMAC signature verification; tenant routing via `merchantToCompany`; reject invalid or cross-tenant events. |
