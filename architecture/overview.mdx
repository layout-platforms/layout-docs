This page describes how Layout Mobile is structured at an infrastructure level — without implementation details, schemas, or internal APIs. It's for technical evaluators and partners who need a clear mental model of the system.

## System components

Layout Mobile has four main surfaces and a backend that ties them together:

| Component | Role | Users |
|-----------|------|--------|
| **Customer app** | Branded iOS app for browsing menu, choosing location, ordering, tracking status, and engaging with loyalty, gift cards, and promotions. | End customers |
| **Merchant dashboard** | Web app for branding, Square connection, menu/locations (synced from Square), order settings, loyalty, promotions, gift cards, and analytics. | Owners and operators |
| **Kitchen panel** | Web-based panel for viewing orders and updating status by location; supports Layout KDS, Square KDS, and Square Expeditor. | Kitchen and store staff |
| **Backend** | APIs, Square sync, webhooks, payment orchestration, push notifications, and secure token storage. | Used by all of the above |

Data and identity are **tenant-scoped**: every request and record is tied to a company (and often a location). There is no shared cross-tenant data layer; isolation is built into the model.

## Data flow (conceptual)

- **Square** is the source of truth for catalog, locations, and payments. Layout connects via OAuth and keeps a secure, per-tenant connection with automatic token refresh.
- **Catalog and locations** flow from Square into the platform via initial sync and ongoing updates (webhooks and daily scheduled jobs). The customer app and dashboard read this data; they don't write catalog back to Square from the app.
- **Inventory** — Sold-out states sync from Square via `inventory.count.updated` webhooks so the app reflects item availability in near real-time.
- **Orders** are created in the platform (customer app → backend), then payment is processed with Square. Order state (pending payment → paid → status updates) is stored in the platform; kitchen and customer app consume it.
- **Kitchen** reads and updates order status. When Layout KDS is used, those updates can drive customer-facing status, push notifications, and iOS Live Activity.
- **Billing** — Merchant subscriptions are managed via Stripe. Billing status (active, past_due, canceled) is synced from Stripe webhooks and gates features like mobile ordering and gift cards at the plan level.

So: **Square owns catalog, locations, and money movement**. **Stripe owns subscription billing**. Layout owns **app configuration, order lifecycle, engagement features, and kitchen display**, and orchestrates payment with Square.

## Authentication and access

- **Customer app** — Users sign in via phone-based authentication. Sessions are validated by the backend for API calls (e.g. checkout, loyalty, gift cards). Tokens are not shared across companies.
- **Dashboard and panel** — Staff and owners sign in to the web app; access is scoped to their company (and optionally location for the panel). Role-based JWT claims (`layoutStaff` and similar) determine what they can see and change.
- **Square** — Connection is per company. OAuth tokens are stored securely and automatically refreshed before expiry. Webhooks from Square are verified (HMAC signature check) before processing. Each webhook is routed to the correct company via a `merchantToCompany` lookup, ensuring a Square event always maps to exactly one tenant.

No customer or merchant credentials are mixed; each channel has clear identity and scope.

## Where things run

- **Customer app** — Native iOS; talks to backend APIs and real-time listeners for order status.
- **Dashboard and panel** — Web apps; talk to the same backend and tenant-scoped data store.
- **Backend** — Hosted serverless/cloud services that handle HTTP and webhook endpoints, Square sync, scheduled jobs, and background push notification delivery. No merchant-hosted infrastructure is required.

Layout runs the backend, dashboard, and panel; merchants don't run servers or databases.

## Integration points

| External system | Layout's role |
|-----------------|----------------|
| **Square** | OAuth with auto-refresh, catalog/location/loyalty/inventory/gift-card sync, payment creation, webhooks for catalog, location, loyalty, inventory, order, and fulfillment events. |
| **Stripe** | Subscription billing; webhooks authoritatively update billing status in the platform. |
| **Push / Live Activity** | Customer notifications (order status, loyalty points earned) and iOS Live Activity for lock-screen order tracking. |
| **Apple App Store** | Each merchant's branded app is submitted and distributed as a distinct App Store listing with per-brand Universal Links. |
