Layout Mobile is built for merchants who already use **Square** for POS, payments, and often loyalty. This page explains how we integrate with Square at a high level — without exposing credentials, URLs, or internal APIs.

## Why Square-first

Many local and multi-location coffee shops run on Square for register, payments, and reporting. Layout adds a **branded mobile app and kitchen visibility** without replacing that stack. We:

- Use **Square as the source of truth** for catalog, locations, and payments.
- Process **payments through Square** so funds and reporting stay in your Square account.
- **Sync** catalog, locations, inventory, and loyalty so the app and dashboard stay aligned with what you manage in Square.
- Support **Square Loyalty**, **Square gift cards**, and **Square discount codes** so the app can surface and use these features natively.

You keep one place to manage menu and money; we keep the app and kitchen in sync.

## Connecting your Square account

Layout uses **Square OAuth 2.0** so you authorize access once from your Square account:

1. From the Layout dashboard, you start **Connect Square**.
2. You're redirected to Square to sign in and grant the requested permissions.
3. Square redirects back with an authorization code; Layout exchanges it for **access and refresh tokens**.
4. Those tokens are stored **securely and per-tenant** (per company). They're used only for that company's API calls — never shared across merchants.
5. The backend **automatically refreshes tokens** before they expire, so your Square connection stays active indefinitely without any action on your part.
6. After a successful connection, Layout runs an **initial sync** of locations and catalog so the dashboard and app have your current data.

Token storage and refresh are handled by the backend; you don't manage tokens yourself.

### Permissions requested

Layout requests the following Square OAuth scopes:

| Scope | Purpose |
|-------|---------|
| `MERCHANT_PROFILE_READ` | Merchant identity and location metadata |
| `ITEMS_READ` | Catalog items, categories, and modifiers |
| `ORDERS_READ` / `ORDERS_WRITE` | Create and read orders |
| `PAYMENTS_READ` / `PAYMENTS_WRITE` | Create and read payments |
| `CUSTOMERS_READ` / `CUSTOMERS_WRITE` | Link Square customers to Layout accounts |
| `LOYALTY_READ` / `LOYALTY_WRITE` | Loyalty program, accounts, and point actions |
| `GIFTCARDS_READ` / `GIFTCARDS_WRITE` | Gift card purchase, reload, and linking |
| `INVENTORY_READ` / `INVENTORY_WRITE` | Sold-out states and inventory counts |

## What we sync

| Data | Direction | How it's kept up to date |
|------|-----------|---------------------------|
| **Locations** | Square → Layout | Initial sync after connect; Square webhooks (location created/updated/deleted); daily scheduled sync as backstop. |
| **Catalog** (items, categories) | Square → Layout | Initial sync after connect; Square webhooks (catalog version updated); daily scheduled sync as backstop. Supports legacy categories and Square Menus. |
| **Inventory** | Square → Layout | `inventory.count.updated` webhooks update sold-out flags on item variations in near real-time. |
| **Loyalty** (if enabled) | Square ↔ Layout | Loyalty program and account data sync on a schedule and after relevant checkout actions; `loyalty.event.created`, `loyalty.program.updated`, and `loyalty.account.updated` webhooks keep data current. |
| **Gift cards** (if used) | Square ↔ Layout | Purchase, reload, linking, and redemption coordinated through the backend; gift card data sourced from Square. |

We do **not** write catalog or locations back to Square from the app or dashboard. Edits to menu and locations happen in Square; Layout reflects them.

### Catalog source modes

Layout supports two Square catalog structures, configured per company:

- **Legacy categories** — Standard Square `CATEGORY` objects. Works with all Square accounts.
- **Square Menus** — Square `MENU_CATEGORY` objects for accounts using the Square Menus feature. Provides richer menu organization when available.

## Payments

- **Checkout** — The customer pays in the app using Square's payment flow (card, Apple Pay). The app sends a payment nonce (and order reference) to the Layout backend; the backend calls **Square's Payments API** to create the payment.
- **Idempotency** — Each payment request is sent with an idempotency key derived from the order and payment context. Retries (network or duplicate tap) don't create a second charge.
- **Settlement and reporting** — All settlement and reporting stay in Square. Layout does not hold card data or settle funds.

So: **Square processes the payment**; Layout orchestrates the request and ties it to the order in the platform.

## Webhooks (Square → Layout)

Layout handles the following Square webhook event types:

| Event | What Layout does |
|-------|-----------------|
| `catalog.version.updated` | Triggers an incremental or full catalog sync for the company. |
| `inventory.count.updated` | Patches sold-out flags on affected item variations. |
| `location.updated` / `location.created` / `location.deleted` | Upserts or removes the location in the platform. |
| `loyalty.event.created` | Queues a push notification job to inform the customer of points earned. |
| `loyalty.program.updated` / `loyalty.program.created` | Syncs loyalty program data. |
| `loyalty.account.updated` | Syncs loyalty balance to the user's account. |
| `customer.deleted` | Unlinks Square customer fields from the Layout user (the Layout account is preserved). |
| `order.updated` | Marks the order ready when the Square order reaches COMPLETED state. |
| `order.fulfillment.updated` | Maps Square fulfillment states to Layout order statuses. |
| `payment.created` / `payment.updated` | Caches payment as a transaction record for customer order history. |

Every webhook is:
1. **Verified** using Square's HMAC signature. Requests that don't verify are rejected.
2. **Routed** to the correct company via a `merchantToCompany` lookup (Square merchant ID → Layout company ID), ensuring cross-tenant leakage is impossible.
3. **Processed** only for the associated tenant's data.

## KDS and orders

- **Order creation** — Orders are created in the Layout platform (customer app → backend). Payment is then created in Square and linked to that order.
- **Layout KDS** — Order status (accepted → making → ready → completed) is stored in the platform and shown on the Layout kitchen panel. Customer-facing status, push notifications, and iOS Live Activity are driven by these status updates.
- **Square KDS** — If you use only Square's kitchen display, Layout doesn't push status; the app shows confirmation and estimated pickup time instead of live status.
- **Square Expeditor** — A two-step fulfillment variant where Square's PREPARED fulfillment state maps directly to Layout's "ready" status, skipping the "making" step. Useful for counter-service workflows.

## Security and isolation

- **OAuth tokens** — Stored per company; used only for that company's Square API calls. Not shared across tenants. Auto-refreshed by the backend.
- **Webhooks** — Signature verification and `merchantToCompany` tenant association ensure we only act on legitimate Square events for the right merchant.
- **Payments** — Customer identity is verified by the backend before creating a payment; order state is checked (pending payment) to avoid duplicate or invalid charges.

For a broader view of how we think about security, see [Security](/security). For reliability (idempotency, retries, sync), see [Reliability](/reliability).
